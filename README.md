# Helheim, Serverless Game Server Orchestrator (Backend)

On-demand Valheim and Vintage Story servers that only cost money while someone is playing.
FastAPI running on AWS Lambda, orchestrating EC2 instance lifecycle through Boto3, with world
state persisted to S3 and DynamoDB between sessions.

A dedicated game server costs the same whether four friends are on it or nobody is. Helheim
boots an instance when a realm is opened, snapshots the world to S3 when the last player leaves
and terminates the box. The monthly bill becomes an hourly one.

Stack: Python, FastAPI, Mangum, Pydantic v2, AWS (Lambda, EC2, S3, DynamoDB), `uv`.

Related: [`helheim.infrastructure`](https://github.com/cristiticu/helheim.infrastructure) (AWS CDK), frontend (React + RTK Query).

## Documentation generated by a multi-agent workflow

The contents of [`docs/`](./docs) were not written by hand. They were produced by a multi-agent
pipeline built on OpenClaw, running Google Gemini:

```
        ┌──────────┐     splits the repo into independent
        │ PLANNER  │───▶  per-module documentation tasks
        └──────────┘
              │  fan-out
      ┌───────┼───────┬───────────┐
      ▼       ▼       ▼           ▼
   ┌──────┐┌──────┐┌──────┐  ┌──────┐   each worker reads only its
   │WORKER││WORKER││WORKER│  │WORKER│   own module and drafts in
   └──────┘└──────┘└──────┘  └──────┘   parallel, no shared context
      └───────┴───────┴───────────┘
              │  collect
        ┌──────────┐     validates drafts against actual
        │ REVIEWER │───▶  source, sends work back if it drifts
        └──────────┘
              │
        ┌──────────┐
        │  PR BOT  │───▶  opens a pull request from a dedicated
        └──────────┘      bot account for human review
```

It produced 5 documented modules and one feature implemented end to end. Nothing merges without
a person approving the pull request.

Some notes from building it:

The workers produced more accurate documentation when each one saw only its own module. Handing
a single agent the whole tree led to confident but wrong claims about how modules interacted.

A reviewer prompted to "check the documentation" approves nearly everything. A reviewer prompted
to find claims in the diff that the source does not support will actually send work back.

Opening a pull request rather than pushing to a branch keeps a person in the loop at the point
where rejecting the work is still cheap.

A pull request the pipeline opened: [#4](https://github.com/cristiticu/helheim.backend/pull/4).

## Architecture

```
Client ──▶ API Gateway ──▶ Lambda (FastAPI via Mangum)
                                │
                ┌───────────────┼────────────────┐
                ▼               ▼                ▼
           DynamoDB           S3               EC2
      (single-table:     (worlds, mods,   (Boto3 start/stop,
       realms, users,     modpacks)        systemd bootstrap)
       portals)
```

### Modular monolith

Requests flow `routers -> services -> persistence`, one package per domain. Routers handle HTTP
and Pydantic validation. Services hold business logic. Persistence hides DynamoDB and S3 behind
interfaces shaped like the models.

```text
src/
├── accounts/      # user account management
├── auth/          # JWT / OAuth2 dependencies
├── realms/        # game servers: realms, portals, worlds
├── routers/       # API endpoints per module
├── shared/        # AWS client wrappers and utilities
├── main.py        # entrypoint and middleware
├── settings.py    # environment-based config
├── exceptions.py  # global error mapping
└── context.py     # correlation IDs
```

### DynamoDB single-table design

Several entity types share one table, discriminated by sort key:

| `s_key`                | Entity                                  |
| ---------------------- | --------------------------------------- |
| `REALM#DETAILS`        | realm configuration and metadata        |
| `USER#<user_guid>`     | user to realm membership                |
| `PORTAL#<portal_guid>` | an active or historical server instance |

### Configuration engine

Server properties and mod sets are injected into a base Linux AMI at boot, through generated
startup scripts and `systemd` units. A realm's mod configuration is therefore data rather than a
bespoke image. World saves, metadata and IP assignment persist across the stop/start cycle.

## Getting started

```bash
uv sync              # install dependencies
./run.local.sh       # run the dev server (ENVIRONMENT=local)
pytest               # run tests
```

Config loads from `.env.<ENVIRONMENT>`, where the environment is `local`, `production` or `test`.
